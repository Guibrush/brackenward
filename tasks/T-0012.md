# T-0012 — an unfinished CI run must not read as a failed gate

Owner: `eng/tools`
Milestone: G1 repair, before G2 starts
Branch: `task/T-0012-ci-pending`
Status: done

## Goal

Make `repo.ps1` report `blocked` rather than `fail` when the latest CI run on
`dev` has not finished, so a gate does not go red for the few minutes after every
merge.

## Context

Observed while landing T-0011. Immediately after the squash-merge, a gate run
reported:

```
| G1.4 | CI is green on dev | fail | last run: in_progress/ |
```

CI completed green two minutes later and the suite returned to 7/7. The gate was
never actually broken; it was asked a question that had no answer yet.

A red gate for reasons unrelated to the work is how people learn to ignore red
gates — the failure `L-019` describes.

## Constraints

One condition branch in `repo.ps1`. No criterion text, threshold, or signature
changes. `fail` must still be reported for a completed run that failed.

## Definition of done

- A queued or in-progress run reports `blocked` with the run state and commit.
- A completed failing run still reports `fail`.
- A cancelled run reports `blocked` and asks for a re-run.
- Demonstrated by running `all.ps1 -Gate G1` immediately after a merge, while CI
  is still running: the gate exits 3, not 1.

## Do not

Do not make the suite exit 0 while CI is unknown. Unknown is not success.

## Return

Standard envelope.
