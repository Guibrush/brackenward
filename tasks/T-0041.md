# T-0041 — The inventory

Owner: `eng/systems`
Milestone: G2 — Vertical slice
Wave: 2B — inventory
Status: open

## Goal

One object owns what the player has: tower instances, upgrades, and which upgrades sit on
which tower. Placement and equipping are free; the inventory is what carries between
levels.

## Rules, from the human

- Acquiring a tower or upgrade adds it to the inventory. **Placement is free.**
- **Duplicates allowed** for towers and for upgrades. Two copies of the same upgrade on
  one tower is allowed, **behind a toggle**.
- **Two upgrade slots per tower**, data-driven.
- Upgrades are **permanent for the run** once applied — replaced is destroyed — but the
  implementation must keep a **removal switch** so the rule can be reversed later.
- Inventory is **uncapped for now**, with a **cap setting** that can be turned on.
- Equipping and applying tiers only happen on a map, between waves (the caller enforces
  timing; this object exposes the operations).
- The inventory dies with the run; nothing persists.

## Definition of done — with planted failures

1. `--check-only` per script, pasted.
2. Selftest passing, printing one summary line, in the shape
   `src/systems/tests/run_state_selftest.gd` uses.
3. **Planted failure A:** with the cap switched on at N, adding the N+1th tower is refused
   with a printed reason, and nothing is added.
4. **Planted failure B:** with duplicate-upgrade allowance toggled off, applying the same
   upgrade twice to one tower is refused with a printed reason; with it on, the same
   sequence succeeds. Both shown.
5. **Removal switch:** show one upgrade removed from a tower back to the inventory with
   the switch on, and refused with the switch off — the permanence rule is a flag, not a
   hardcode.
6. Tiers survive the round trip: a tower at tier 3 taken back into the inventory and
   placed again is still tier 3, with its equipped upgrades attached.
