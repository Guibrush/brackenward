# T-0063 — Input must actually reach the game

Owner: `eng/gameplay`
Milestone: G2 — Vertical slice
Wave: 2F — playability
Status: open

## The bug

In the running game the panel's rows render but **nothing can be selected**: clicking a row does
nothing, pressing Enter does nothing. The demos pass because they call `handle_input()` and
`activate()` directly — they test the methods, not whether anything ever delivers an event.

Same class as the invisible panel (T-0062): the code works when called by a test, and not when
driven by a player.

## What to establish first

Find out, by evidence, which of these is true — do not assume:

- the panel's `handle_input()` is never called by anything in the real tree;
- events are consumed by the arena's `_unhandled_input` before the panel sees them;
- the rows are `Button`s that need `mouse_filter` / focus settings to receive clicks and keys;
- or something else.

Report the actual cause with the command or log line that shows it.

## The fix

Make the real input path work:

1. **Mouse**: clicking a row selects it; clicking a build tile with a tower armed places it;
   clicking a placed tower opens its actions.
2. **Keyboard/pad**: Up/Down moves focus between rows, Enter confirms, Escape backs out —
   through the same `game_*` actions the map screen uses.
3. One owner for input in the level screen. If the panel and the arena both read input, decide
   which wins and say why; do not leave two readers racing.

## Definition of done — the evidence rule for this one

**Every assertion must drive the real boot path through the real input pipeline.** No calling
`handle_input()` or `activate()` directly; use `get_viewport().push_input(event)` (or
`Input.parse_input_event`) on the real tree so the event travels the same route a player's
does.

1. `--check-only`, pasted.
2. From menu → Start Game → map → first node, send a real mouse click on the **arrow** row and
   show it becoming selected/armed.
3. Send a real click on a build tile and show the tower placed.
4. Send real `game_confirm` pressed twice from the menu path and show the same happens by
   keyboard.
5. **Planted failure:** stub out the input route (in a copy) and show the demo failing to select
   anything — proving the test would have caught today's bug.
6. A rendered frame after a successful selection is **optional** here; the event log is the
   evidence.
